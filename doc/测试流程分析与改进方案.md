# 阶段验收测试流程分析与改进方案

> 分析日期：2026-10-31
> 分析对象：分支 `feature/mobile-adapt`，Godot 4.7.2，8 套 headless 验收（552 条断言）
> 结论依据：本机实测耗时 + 本次会话中实际发生的 3 次「命令被取消 / 后台化」事件

---

## 1. 结论摘要

| 排名 | 瓶颈 | 实测证据 | 占端到端时间 | 改进后目标 |
|---|---|---|---|---|
| ① | **用例执行**：真实物理帧等待 | `stage_a` 26.3s 中 24s 是「6 方向 × 4 秒冲撞」；`stage_b` 39.6s 中约 30s 是 2–3 秒级的等待与逐帧循环 | **93%** | 全量 ≤25s |
| ② | **反馈链路**：每次改动都手敲命令跑全量 | 一次全量 ≈70.7s + 一次 shell 往返；本会话中 3 次长命令被判定「需要等待」而取消/后台化 | 每轮 1–2 分钟 | fast 组 ≤5s |
| ③ | **环境准备**：BOM / 编码 / PATH 噪声 | 7 个文件带 UTF-8 BOM，导致每次扫描都打 `Parse Error`；PowerShell 中文输出乱码；新终端不继承 PATH | 隐性 10–20s/轮 | 0 噪声 |
| ④ | **验收审批**：决策文档 5 轮往返 | 需求确认走了一→五轮，每轮一次问答往返，实现开始前累计约 4 小时 | 前置成本 | ≤2 轮 |

**一句话**：慢的不是引擎，是**「每次都用真实时间跑全量」+「靠人肉敲命令」**。引擎冷启动只占 5%（0.46s/套），真正的 93% 花在等物理帧上。

## 2. 度量基线（实测）

### 2.1 各套 suite 耗时

| Suite | 分组 | 耗时 | 断言 | 说明 |
|---|---|---|---|---|
| `stage_a_check` | slow | **26.3s** | 9 | 6 个方向各「冲撞 4 秒」，合计 24s 真实等待 |
| `stage_b_check` | slow | **39.6s** | 132 | 多处 2–3 秒级等待（开局观测、复活、自动接近、锁定滞回） |
| `i18n_settings_check` | fast | 2.0s | 76 | 加载字体与中英文案表 |
| `mobile_layout_check` | fast | 0.8s | 102 | 纯计算 |
| `settings_readability_check` | fast | 0.6s | 65 | 纯计算 |
| `display_preset_check` | fast | 0.5s | 87 | 纯计算 |
| `touch_contract_check` | fast | 0.5s | 31 | 纯计算 |
| `stage_c_check` | fast | 0.4s | 50 | 纯数据/服务层 |
| **合计** | — | **70.7s** | **552** | fast 4.8s / slow 65.9s |

### 2.2 启动开销占比

| 项 | 实测 |
|---|---|
| 单次引擎冷启动（`--headless --quit`） | 0.46s |
| 最快 suite 全程 | 0.47s（≈ 启动 + 10ms） |
| 8 套启动总开销 | ≈ 3.7s，占 70.7s 的 **5%** |

→ **优化方向不是「减少进程数」，而是「减少等待」。**

### 2.3 反馈链路事件（本次会话实录）

| # | 事件 | 触发原因 |
|---|---|---|
| 1 | 「导入 + 8 套验收」合并成一条命令 → 被判定为长任务而**跳过** | 单条命令预期 >90s |
| 2 | 再次尝试同类命令 → **跳过** | 同上 |
| 3 | 只跑 `stage_c_check`（应 ~2s）→ **用户取消** | 前两次跳过已让人失去耐心 |

其中第 3 次实际耗时 0.4s —— 说明**问题不在真实耗时，而在「命令形态让人无法预期」**：看不到进度、不知道要等多久、失败也没有摘要。

## 3. 瓶颈定位（按环节拆解）

### 3.1 环境准备

| 项 | 现状 | 具体影响 |
|---|---|---|
| 引擎路径 | 不在标准位置，靠硬编码 `D:\godot_program\...` | 换机/新终端即失败 |
| PATH 继承 | 新 shell 读不到刚改的用户 PATH | 每次要手动拼 `$env:Path` |
| **UTF-8 BOM** | `hud.tscn`、`hud.gd`、`enemy_visual.gd`、`stage_b_check.gd`、`enemies.json`、`en.json`、`zh.json` 共 7 个文件带 BOM | 每次扫描打 `ERROR: Parse Error: Expected '['`，被当成真失败排查过；也污染日志 |
| 输出编码 | PowerShell 5.1 默认按 GBK 解码 → 中文断言显示为乱码 | 读日志成本高，曾误判过数值 |
| 资源导入 | `--import` 与测试混在一条命令里 | 单条命令不可控、耗时不可预期 |

### 3.2 用例执行（主要瓶颈，93%）

| 现象 | 证据 | 根因 |
|---|---|---|
| `stage_a` 26.3s | 6 个方向 × `await physics_frame` × 240 帧 | 用真实时间模拟 4 秒推墙 |
| `stage_b` 39.6s | 开局 3s 观测 + 复活 2s + 自动接近/滞回多段等待 | 游戏常量写死在脚本里（`RESPAWN_DELAY = 2.0`、`HURT_INVULN = 0.3`），测试无法注入短值 |
| 8 套串行、无并行 | 物理帧等待无法并行化 | 单进程、单线程物理 |
| 无分段耗时 | 失败时只知道「这一套慢」，不知道慢在哪个函数 | 没有 per-test 计时 |

**关键发现**：`data/actors/player.json` 里已经把 `auto_attack_hold_seconds`、`aggro_latch_timeout` 等时间参数外置了 —— 说明「数值外置」的约定是有的，只是**死亡/受击/复活这几个时间常量还没外置**，而它们恰好是 stage_b 最长的等待来源。

### 3.3 结果反馈

| 现象 | 影响 |
|---|---|
| 每次手敲 `godot --headless --path ... res://tests/x.tscn` | 命令长、易错、无法批量 |
| 输出直接刷屏，只看最后 5 行 | 失败需回读代码定位 |
| 无退出码聚合 | 跑 8 套要人工比对 8 次 |
| 失败摘要缺失 | 一次失败要 3–5 分钟才能定位到断言 |

### 3.4 缺陷反馈闭环

| 现象 | 影响 |
|---|---|
| 无 CI（`.github/` 不存在） | 回归全靠人；分支上已有「历史失效断言」先例（适配方案 §6.2 记录了 2 条） |
| 改动 → 全量跑 → 改 → 再全量 | 本次 stage_c 一个功能跑了 3 轮 |
| 断言消息缺实际值 | 部分失败只报「不满足」，需加临时打印 |

### 3.5 验收审批

| 现象 | 影响 |
|---|---|
| 需求确认走了五轮文档 | 每轮一次往返，实现前累计约 4 小时 |
| 每轮只回答「当轮新出现的问题」 | 旧问题反复搬运（N03–N08 出现 3 次） |
| 缺少「推定决策」机制 | 直到第五轮才引入（D-15） |

## 4. 改进方案

### 4.0 已完成（本次会话内落地）

| 改动 | 效果 |
|---|---|
| 新增 `tools/run_tests.ps1`：分组运行、聚合耗时/断言/失败摘要、`-Import` 独立开关、fast 组 20s 超时 | 单命令一次跑一组，输出一张表 |
| 清除 7 个文件的 UTF-8 BOM | 日志里不再有无害但误导的 `Parse Error` |
| 修正运行器判定：以「结果：全部通过」+ FAIL 计数为准，`Parse Error` 仅在 0 断言时才算失败 | 消除误报 |
| 分组：fast 6 套（4.8s）/ slow 2 套（65.9s） | 日常改动只跑 4.8s |

### 4.1 P0：反馈链路（今日生效）

| 环节 | 职责 | 输入 | 输出 | 时间节点 | 验收标准 |
|---|---|---|---|---|---|
| 开发改代码 | 开发（我） | 改动 | 可运行代码 | — | — |
| **fast 自检** | 开发 | `tools/run_tests.ps1 -Group fast` | 6 套结果表 | **每次改动后 ≤10s** | 全 PASS 才继续 |
| **slow 校验** | 开发 | `-Group slow` | 2 套结果 | **每完成一个功能/提交前** | 全 PASS 才提交 |
| 提交 | 开发 | 变更 + 测试同 commit | commit | 每功能一次 | 一功能一 commit，测试同行 |

**规则**：任何时候不得把「导入 + 全量」塞进一条交互命令；一律用 runner，且交互态只跑 fast 组。

### 4.2 P1：把等待降下来（本周）

| 动作 | 做法 | 预估效果 |
|---|---|---|
| **时间参数外置** | `RESPAWN_DELAY`、`HURT_INVULN`、`RESPAWN_INVULN`、`DEATH_LINGER` 移入 `data/actors/player.json` / 敌人定义；测试用注入短值（0.1s） | `stage_b` 39.6s → **≈12s** |
| **收敛 stage_a 方向数** | 4 秒 × 6 方向 → 2 个轴向 + 2 个对角各 2s（另一侧由对称断言覆盖） | 26.3s → **≈8s** |
| **per-test 计时** | 每个 `_test_*` 前后打 `[TIME] name=xx ms=yy` | 失败定位从分钟级 → 秒级 |
| **失败摘要进 runner** | 已实现（打印前 3 条 FAIL），补「断言所在文件:行号」 | 定位 ≤30s |

目标：全量 70.7s → **≤25s**；届时 fast/slow 的划分可以放宽为「全量一次跑」。

### 4.3 P2：防止回归漏网（下周）

| 动作 | 做法 | 时间节点 | 验收标准 |
|---|---|---|---|
| **CI 接入** | GitHub Actions（公开仓库免额度），push 触发：`--import` → `run_tests.ps1 -Group all` | 下周内 | 每次 push ≤3 分钟出结果，红灯阻止合并 |
| **变更-测试映射** | 表驱动：改 `scripts/items/**` → 跑 stage_c；改 `scripts/actors/**` → stage_a/b；改 `autoload/display_adapter.gd` → 布局 4 套 | 随 CI 一起 | 单功能改动只跑相关 1–3 套 |
| **决策流程收敛** | 需求确认单轮 + 推定机制（D-15 已建立）；文档评审 ≤2 轮 | 立即 | 新需求从提出到开工 ≤1 轮往返 |

### 4.4 审批环节的具体改法

| 现状 | 改法 |
|---|---|
| 五轮问答文档，每轮只答新问题 | 单份文档 + 「推定决策」：连续两轮未答即按建议执行并标注 `[推定]` |
| 实现后集中验收 | 拆成「每功能一个 commit + 该功能断言」，随时可验收 |
| 验收标准散落在对话里 | 固定为：该功能断言全绿 + 全量无回归 + 文档同步 |

## 5. 衡量指标与预期效果

| 指标 | 现状（实测） | 目标 | 预期收益 |
|---|---|---|---|
| 单次反馈时长（改完代码到看到结果） | 70.7s 全量 + 命令往返 | **≤5s（fast）** | 迭代 10 倍加速 |
| 全量回归时长 | 70.7s | **≤25s**（P1 后） | 提交前全量不再是负担 |
| 每个功能平均迭代轮数 | 3 轮（stage_c 实录） | **≤2 轮** | 少一轮即省 1–2 分钟/功能 |
| 失败定位时间 | 3–5 分钟（翻日志 + 编码乱码） | **≤30s**（FAIL 行带值与位置） | 排障成本降 90% |
| 回归发现时机 | 下次手跑（可能几天后） | **push 后 ≤3 分钟** | 失效断言不会过夜 |
| 环境噪声（BOM/编码/路径） | 每轮 1–2 次 | **0** | 少走弯路 |
| 决策往返轮次 | 5 轮 | **≤2 轮** | 前置时间从 4 小时 → ≤1 小时 |
| 单条命令可预期性 | 常被判定「需要等待」 | 全部 <30s 或走 runner 后台 | 不再出现跳过/取消 |

**综合预期**：一个典型功能（改代码 → 自检 → 全量 → 提交）的挂钟时间从 **约 8–12 分钟** 降到 **约 2–3 分钟**。

## 6. 风险与回退

| 风险 | 缓解 |
|---|---|
| 时间参数外置后，测试用 0.1s 注入，可能掩盖真实时序 bug（如无敌帧与攻击间隔的相互作用） | 保留 1 套「真实时序」慢测（stage_b 的死亡复活段）在 slow 组，不注入短值 |
| 缩减 stage_a 方向数导致漏测某一侧碰撞 | 用对称断言覆盖：断言「撞墙后仍在图内」对四个方向均已成立时，另一侧等价；对角保留两条 |
| fast 组 20s 超时误杀慢机器 | 超时按组配置（fast 20s / slow 180s），并允许 `-TimeoutSec` 覆盖 |
| CI 在 Linux runner 上行为差异 | 先在本地 `--headless` 全绿（已满足），CI 首跑只做「观察模式」不阻塞合并 |

3. **下周**：接 GitHub Actions（push 触发，8 套 + import），红灯阻止合并。
