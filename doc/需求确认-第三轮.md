### N01【矛盾】AI 资产到底要不要人工重绘？

**问题**
Q11 主选项 D =「AI 辅助出图 **+ 人工重绘**」；C01 你选 D2 =「**可接受但需披露**」，并备注「可能大部分资产由 AI 生成，登记表标注即可」。两者的流程强度不同：前者要求每张图都重绘，后者允许直出后披露。

**背景与影响**

**选项**

| 选项 | 做法 | 利 | 弊 |

| A | **直出即可进包**（登记 + 披露） | 最快 | 一致性差、易返工；部分平台要求披露 |

### N03【安全冲突】C03-D2=B（HMAC 防改档）+ C12「仓库公开」= 密钥必然泄露

**问题**
HMAC 的防护力来自密钥保密。仓库公开后，任何硬编码或提交进 Git 的密钥都等于公开；而单机游戏的客户端也必然可被逆向。二者叠加时，HMAC 退化为「比 CRC 稍复杂一点的混淆」。

**背景与影响**
- 若坚持 HMAC：需要「密钥不入库 + 构建时注入」的机制（`.gitignore` 的本地密钥文件 + 构建脚本参数），否则等于自欺。
- 你已选 Q02=A（内部 demo、无排行榜、无交易），「防作弊」没有实际对手，防护目标应回到「防误改 / 防坏档」。

**选项**

| 选项 | 做法 | 利 | 弊 |
|---|---|---|---|
| A | **改回 CRC + `schema_version`**（防误改，不防人为） | 与「内部 demo、公开仓库」完全自洽；实现 2 小时 | 手动改档仍可行（本项目无实际损失） |
| B | **HMAC + 密钥本地不入库**（构建时注入，缺失则降级为 CRC） | 保留了防改能力，且不泄露 | 需要构建脚本与 CI secret 配套；本地跑测试要准备密钥 |
| C | HMAC + 密钥硬编码（接受公开） | 实现最简 | 名为防护实为混淆，且会被当作「假安全」 |

### N04【范围缺口】C03-D1=B（引入 `.tres`）迁移到哪一层？

**问题**
现有数据全部是 `data/**/*.json`，由 `DataRegistry` 只读加载并校验（actors、maps、i18n、targets）。「引入 `.tres`」没说清是**全部迁移**还是**只迁新增的物品/装备/掉落**，也没说与 JSON 如何共存。

**背景与影响**
- 全量迁移：`DataRegistry` 要重写、i18n 与地图格式要动、7 套验收里凡读 JSON 的断言都要改。粗估 +3–5 人日，会把 C13 的「10–15 人日」推到 **13–20 人日**。
- 只迁新增：`DataRegistry` 变成双通道（JSON 基础表 + Resource 定义表），需明确边界（哪些是「定义型」数据），否则长期形成两套真值。
- 还牵涉目录规范（`data/<模块>/*.tres`）与「`.tres` 里能否引用脚本/图标」的约定。

**选项**

| 选项 | 做法 | 利 | 弊 |
|---|---|---|---|
| A | **只让新增的 items / equipment / loot 用 `.tres`**，actors / maps / i18n 保持 JSON | 阶段 C 改动最小；物品可在编辑器里可视化配置 | `DataRegistry` 双通道，需写清边界 |
| B | **全部迁 `.tres`** | 单一真值来源、类型安全 | +3–5 人日，7 套验收全要改 |
| C | **保持 JSON**（撤销 C03-D1 的 B） | 与现有架构零摩擦 | 物品/装备配置只能手写 JSON |
