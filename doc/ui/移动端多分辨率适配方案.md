# 移动端多分辨率适配方案

> 适用范围：以移动端为首要目标平台的多分辨率适配（PC 作为「大屏档」纳入同一套规则）。
> 状态：方案确认稿（未落地代码）。
> 取代关系：本文取代《1080p 分辨率适配方案》的优先级结构；后者中「资产规格锁定」与「不改 `Iso` 逻辑常量」两条结论继续有效，其余以本文为准。
> 关联文档：《原始文档1.txt》第 6 章「美术资产规范」、第 8.5 节「性能」、第 12 节「风险」。

---

## 0. 摘要

1. **项目当前是「矢量占位 + 程序化绘制」阶段**，零贴图、零模型，现在锁定资产规格与适配规则，迁移成本为零；越晚改，返工的是已产出素材。
2. **移动端无法同时满足「像素 1:1」与「视野恒定」**。必须引入「逻辑渲染分辨率」这一中间层：世界在固定逻辑分辨率内渲染，屏幕端只做缩放；1:1 只在特定分辨率组合下成立，其余情况接受轻微软化。
3. **当前最大的阻塞不是渲染管线，而是 UI**：`hud.tscn` 有 40 处绝对 `offset_*`、零 `anchor_*`，`HP_FILL_MAX` 与字号全部硬编码。在 20:9 手机上逻辑视口会变成 1600×720，右侧按钮将整体脱离屏幕边缘——这是必须先偿还的债。
4. **`project.godot` 缺少三项移动端前提**：横屏锁、`stretch/scale_mode`、纹理压缩开关。文档层面必须先补齐基线，否则后续读者会误判「已具备移动端基础」。

## 1. 实施目标

### 1.1 总目标

在不改动 `Iso.TILE_W/H = 64/32`、不改动 `data/actors/*.json` 数值、不破坏 `stage_a_check` / `stage_b_check` 断言的前提下，建立一套**以移动端为第一约束**的多分辨率规则：

- 世界渲染与屏幕尺寸解耦，屏幕尺寸变化只影响「看清多少」与「缩放多少」，不影响逻辑；
- UI 尺寸以物理尺寸（dp）为准，不随世界缩放一起缩小；
- 已有 PC 1080p 需求收敛为「大屏档」，与移动端共用同一套口径，而不是两套方案。

### 1.2 可判定效果

| 目标 | 判定标准 |
|---|---|
| 尺寸无关 | 16:9 / 19.5:9 / 20:9 / 4:3 / 折叠屏五类屏幕下，HUD 不越界、不重叠、不压安全区 |
| 视野可控 | 同档位设备可见格数偏差 ≤10%；极宽屏不出现「横向多看 25% 格」导致的难度失真 |
| UI 可点 | 所有可交互元素物理尺寸 ≥44 dp，主操作 ≥56 dp；单指操作无遮挡 |
| 性能达标 | 最低可接受设备（中端 1080p 机）在默认档位稳定 60 FPS；低端档保底 30 FPS 不烫手 |
| 逻辑零改动 | `Iso` 常量、JSON 数值、两套 headless 验收脚本全部不变且通过 |
| 可配置 | 「画质档位」「UI 缩放」「视野档位」进入 `GameSettings` 并持久化 |

### 1.3 范围边界

**纳入**：显示口径与缩放策略、视野与宽高比规则、安全区契约、UI/世界解耦、设备分级与画质档、触控交互契约、资产规格与包体预算、验收矩阵。

**不纳入**：美术资产的实际量产（仅锁定规格）、实时 3D 管线（与当前 2D 等距 `y_sort` 架构不兼容）、竖屏模式（等距 RPG 锁定横屏）、音视频与网络。

## 2. 现状基线与移动端缺口

### 2.1 渲染与配置现状

| 项目 | 现状 | 出处 |
|---|---|---|
| 基准分辨率 | 1280×720 | `project.godot` `[display]` |
| 缩放模式 | `canvas_items` + `aspect=expand` | 同上 |
| 渲染器 | GL Compatibility（`renderer/rendering_method.mobile` 亦为 `gl_compatibility`） | 同上 |
| 纹理过滤 | nearest（`default_texture_filter=0`） | 同上 |
| 逻辑网格 | 64×32（`Iso.TILE_W/H`），1 世界单位 = 1 逻辑像素 | `scripts/utilities/iso.gd` |
| 相机 | 无 `zoom`（默认 1.0），仅偏移与平滑 | `scenes/actors/player/player.tscn` |
| 地图 | 32×32 格（1024 格） | `data/maps/test_map_01.json` |
| 美术资源 | 无贴图、无模型，全部 `draw_*` 程序化绘制 | `*_visual.gd`、`ground_renderer.gd`、`prop_node.gd` |
| 字体 | `fonts/Teko.ttf`（未入库） | — |

### 2.2 代码层缺口

| 现象 | 证据 | 后果 |
|---|---|---|
| 横屏锁缺失 | `project.godot` 无 `display/window/handheld/orientation` | 部分机型可能竖屏启动，布局彻底失效 |
| 无缩放档位控制 | 无 `stretch/scale_mode`（integer/fractional） | 无法在整数缩放与平滑缩放间按设备选择，像素风易出现抖动 |
| 无纹理压缩配置 | 无 `rendering/textures/vram_compression/*` | 后期接入贴图时显存按 RGBA8 全额占用，低端机易 OOM |
| UI 全绝对坐标 | `hud.tscn` 40 处 `offset_*`、0 处 `anchor_*`；`HP_FILL_MAX=276`、字号 16–28 硬编码 | 20:9 下逻辑视口变 1600×720，右侧按钮脱离边缘；4:3 下底部元素上浮至屏幕中部 |
| 设置面板绝对定位 | `settings_panel.gd` 的 `PANEL_POS(320,60)` / `PANEL_SIZE(640,600)` | 小屏溢界、大屏过小 |
| 触控热区固定 | `touch_button.radius=56`、`virtual_joystick.base_radius=84` / `knob_radius=38` | 小屏物理尺寸偏小，误触率上升 |
| 无安全区处理 | 全仓库无 `get_display_safe_area` 调用 | 刘海/挖孔/手势条遮挡血条与按钮 |
| 触摸与鼠标双分支 | `virtual_joystick.gd`、`touch_button.gd` 的 `_gui_input` 同时处理 `InputEventScreenTouch` 与 `InputEventMouseButton` | 移动端默认开启触摸模拟鼠标，单指走两条路径，需保证幂等（当前依赖 `_held` / `_pointer` 守卫） |
| 无生命周期处理 | 仅 `input_manager.gd` 在失焦时补 `target_select_released` | 切后台/来电后无暂停与设置落盘保证 |

### 2.3 核心取舍：1:1 与视野恒定不可兼得

原方案承诺「1920×1080 + `zoom=1.5` + 视野 900 格 + 像素 1:1」，其隐含前提是**视口尺寸 == 屏幕物理尺寸**。移动端打破该前提：

- 屏幕短边从 720 到 1440 物理像素不等，DPR 2.0–3.5；
- 宽高比从 16:9 到 20:9，「可见格数」随长边线性增长。

因此在移动端必须二选一或以中间层折中：

| 取舍 | 做法 | 代价 |
|---|---|---|
| 保像素 1:1 | 世界按 1:1 渲染，可见格数随屏幕浮动 | 20:9 比 16:9 多看 25% 世界，关卡与刷怪密度失真 |
| 保视野恒定 | 缩放跟随屏幕面积，格数固定 | 非整数缩放，像素出现软化与轻微抖动 |
| **折中（推荐）** | 引入「逻辑渲染分辨率」，视野按面积归一，屏幕端缩放 | 1:1 只在特定组合成立；其余档位接受软化，但换取一致的关卡体验 |

**结论**：移动端采用折中方案。1:1 不是全局承诺，而是「逻辑渲染分辨率 == 屏幕物理像素 / 整数倍」时的特例。

## 3. 实施方法

### 3.1 显示抽象层：三口径

全文所有尺寸必须归属且仅归属以下一个口径，禁止混用：

| 口径 | 单位 | 用途 | 示例 |
|---|---|---|---|
| 物理像素 | px | 屏幕/纹理采样、填充率预算 | 2400×1080 |
| 设备无关单位 | dp | UI 布局、热区、字号 | 热区 ≥44 dp |
| 世界单位 | wu | 游戏逻辑、碰撞、寻路、`Iso` 网格 | 图块 64×32 wu |

**换算链**

```text
dp    → px ：px = dp × (dpi / 160) × ui_scale
wu    → px ：px = wu × zoom × render_scale
```

其中 `render_scale` = 逻辑渲染分辨率 / 屏幕分辨率，`zoom` 为 `Camera2D.zoom`。两者分离是「世界可缩放、UI 不受影响」的实现基础。

### 3.2 逻辑渲染分辨率与缩放策略

**方案要点**

1. 世界层在 `SubViewport` 中以「逻辑渲染分辨率」渲染，尺寸 = 屏幕物理尺寸 ÷ 渲染倍率，并 clamp 到 `[960×540, 1920×1080]`。
2. 渲染倍率按画质档取值（0.7 / 0.85 / 1.0），是移动端控制填充率最有效的手段。
3. UI 层独立 `CanvasLayer`，跟随窗口逻辑坐标 + 安全区内缩，不吃 `render_scale`。
4. 世界内容以 nearest 采样放大到屏幕，`stretch/scale_mode` 按档位选择（像素风偏 integer，写实风偏 fractional）。
5. 渲染倍率与缩放档位均为**离散枚举**，禁止无级缩放，避免非整数采样下的像素抖动与摩尔纹。

**1:1 成立条件（写进规格，作为唯一验收口径）**

```text
逻辑渲染分辨率 == 屏幕物理像素 ÷ 整数  →  世界像素与屏幕像素 1:1
```

不满足时允许软化，但不得出现「部分元素 1:1、部分元素 0.85×」的混排。

### 3.3 视野口径与宽高比处理

**口径定义**：视野以「可见格数」而非「世界单位矩形」表述，因为格数直接决定关卡节奏与刷怪密度。

单格等距菱形面积 = 64×32/2 = 1024 px²，可见格数 = (逻辑宽/zoom) × (逻辑高/zoom) ÷ 1024。

| 场景 | 逻辑视口 | zoom | 可见世界区域 | 等效格数 |
|---|---|---|---|---|
| 现状 720p PC | 1280×720 | 1.0 | 1280×720 | ≈900 |
| PC 1080p 大屏档 | 1920×1080 | 1.5 | 1280×720 | ≈900 |
| 移动 16:9 | 1280×720 | 1.5 | 853×480 | ≈400 |
| 移动 20:9 | 1600×720 | 1.5 | 1067×480 | ≈500 |
| 移动 20:9（归一后） | 1600×720 | 1.118 | 1431×644 | ≈900 |

**规则**

- **归一公式**：`zoom = sqrt(逻辑视口面积 ÷ 基准面积)`，基准面积取 1280×720。使可见格数与宽高比无关。
- **档位区间**：移动端 `zoom ∈ [1.1, 1.5]`，`clamp` 后不再随屏幕变化。
- **极宽屏**（≥21:9）：按上述公式归一后横向视野仍偏大，改为「长边上限」——超出部分收进 UI 区域，不额外增加可见格。
- **4:3 平板**：宽高比导致水平视野减少约 25%，允许单独启用 `zoom` 微调档，而非裁切 UI。
- **禁用做法**：不允许用 `aspect=keep` + 黑边解决宽高比问题（黑边在手机上不可接受）。

### 3.4 安全区契约

1. HUD 容器不直接锚定窗口矩形，而是锚定「窗口矩形内缩 `safe_area` 后的矩形」。
2. 内缩量：`24–40 dp`，按设备档位取值；`get_display_safe_area()` 返回空或全屏时按 0 处理。
3. 安全区变化（旋转、折叠屏展开、分屏）时 HUD 必须重排一次，且重排不丢状态。
4. 世界层**不**受安全区约束（避免相机中心偏移导致手感不一致），仅 UI 内缩。

### 3.5 UI 与世界解耦（架构约束）

| 层 | 归属 | 缩放来源 | 约束 |
|---|---|---|---|
| 世界 | `SubViewport` | `zoom` × `render_scale` | 不得依赖窗口像素尺寸计算布局 |
| HUD | 独立 `CanvasLayer` | `content_scale_factor` / 锚点 | 不得使用绝对 `offset_*` |
| 浮层（飘字、锁定框） | 世界层内 | 同世界 | 不得跨层引用 UI 坐标 |

**硬性要求**

- `hud.tscn` 全部改为 `anchor_*` + `Container`；`HP_FILL_MAX` 改为按 `bar.size.x × ratio` 计算。
- 字号改为 dp 语义（基准 1080p 下 20/22/24，随 `ui_scale` 统一缩放，不做逐控件硬编码）。
- `settings_panel` 改为居中锚点 + 相对尺寸（约 0.7 宽 × 0.75 高）。

### 3.6 设备分级与画质档位

| 档位 | 目标设备 | 渲染倍率 | 纹理格式 | 目标帧率 | 特效上限 |
|---|---|---|---|---|---|
| 低 | Adreno 610 / Mali-G52 及以下 | 0.7 | ASTC 4×4 | 30（保底）/ 60（可选） | 飘字 ≤6、无阴影、无受击闪光叠加 |
| 中 | Adreno 640 / Mali-G72 级 | 0.85 | ASTC 4×4 | 60 | 飘字 ≤12、简化阴影 |
| 高 | Adreno 7xx / A15 及以上 | 1.0 | ASTC 4×4 | 60 | 全开 |

- 档位由首次启动的设备探测给出默认值，用户可在设置中覆盖，结果写入 `GameSettings`。
- 降级顺序固定：渲染倍率 → 特效数量 → 阴影 → 飘字，禁止跳级降纹理质量（会造成观感断层）。
- 「最低可接受设备」定义为：中档 1080p、4 GB 内存、Adreno 640 级 GPU，默认档位下稳定 60 FPS。

### 3.7 触控与交互契约

| 条目 | 要求 | 现状对照 |
|---|---|---|
| 热区 | 一般 ≥44 dp，主操作（攻击）≥56 dp | `touch_button.radius=56`、摇杆 `base_radius=84` 在 1080p 基准下约 0.52–0.78 cm，达标；小屏需按 `ui_scale` 补偿 |
| 摇杆死区 | 0.08（与 `InputManager` 现有阈值一致） | 已一致 |
| 按下反馈 | ≤100 ms 内可见（高亮/缩放） | `touch_button` 已有 `_held` 高亮 |
| 多指并发 | 摇杆 + 攻击 + 目标选择三指互不抢占 | 摇杆按 `event.index` 跟踪，按钮未区分手指，需验证 |
| 触摸/鼠标幂等 | 单指只触发一次按下与一次抬起 | 依赖 `_held` / `_pointer` 守卫，需真机验收 |
| UI 吞事件 | 按钮区域不得传导为移动/攻击 | 已用 `MOUSE_FILTER_STOP` |
| 禁用态 | 无可用目标时置灰且不响应 | `touch_button.set_disabled` 已实现 |
| 暂停态 | 暂停/切后台时不接收攻击与选择 | 仅失焦补 release，缺暂停门控 |

### 3.8 资产规格与移动端体积预算

**规格（不变项）**：图块 96×48、玩家画布 128×160、小怪 96×128、精英 160×192、UI 图标 64×64、面板 512×512 九宫格；精灵 `scale≈0.667`（96px 美术对应 64 wu）；原点取脚底；1 wu = 1 逻辑像素；命名沿用《原始文档1.txt》6.3。

**体积预算（新增）**

| 项目 | 预算 | 说明 |
|---|---|---|
| 首包资源 | ≤60 MB | 引擎 + 字体 + 首关纹理与音频 |
| 增量下载 | 每章 ≤40 MB | 按章节分包，Wi-Fi 预取 |
| 纹理显存（垂直切片） | ≤40 MB | 4 向约 28 MB 未压缩，ASTC 4×4 后约 5–7 MB；8 向换装 55–70 MB 需 ASTC |
| 音频 | ≤15 MB | Ogg Vorbis，单文件 ≤1 MB |
| 单图集上限 | 2048×2048 | 兼顾低端机最大纹理尺寸 |

**必备前置**：先出「试验资产包」（1 块地面、1 个四向角色、1 只怪物、1 棵树、1 栋建筑、1 套 UI 面板），在真机上验证缩放、滤镜、纹理边缘、帧对齐、排序与碰撞，再批量生产。

### 3.9 PC 大屏档（1080p）

同一套规则下的一个档位，不再单列方案：

| 项 | 取值 |
|---|---|
| 逻辑渲染分辨率 | 1920×1080（不缩放，`render_scale=1.0`） |
| `zoom` | 1.5（归一后 ≈900 格，与 720p 现状一致） |
| UI | 同 dp 规则，`ui_scale` 默认 1.0 |
| 窗口策略 | 窗口模式最小 1280×720；全屏跟随显示器原生分辨率 |

## 4. 性能开销说明

### 4.1 填充率与帧预算

| 指标 | 720p | 1080p | 判断 |
|---|---|---|---|
| 全屏像素 | 0.92 Mpx | 2.07 Mpx（×2.25） | — |
| 60 FPS 单层填充预算 | 55 Mpx/s | 124 Mpx/s | PC 无压力 |
| 实际（精灵 overdraw 2–3 层） | 165–250 Mpx/s | 250–370 Mpx/s | 桌面集显 <15% |
| 中端手机（Adreno 610 / Mali-G52） | 可 60 FPS | 需 0.7–0.85 倍渲染，否则掉帧发热 | **移动端瓶颈** |
| CPU / 逻辑 | 不变 | 不变 | 与分辨率无关 |

- 1080p 全分辨率 + 3 层 overdraw 接近中低端 LPDDR4x 有效带宽上限，故**低档默认渲染倍率取 0.7**，中档 0.85。
- 地面 1024 格当前为一次性 `draw_colored_polygon`（静态 canvas item）；改 TileMapLayer 后单屏 400–900 tile，draw call 仍在个位数。
- 12 个敌人的 AI 每 0.25 s 寻路一次，与分辨率无关。

### 4.2 内存与包体

| 项 | 720p | 1080p / 移动基准 | 说明 |
|---|---|---|---|
| 垂直切片纹理（未压缩） | ≈13 MB | 28 MB（8 向换装 44–70 MB） | 4 向垂直切片 |
| ASTC 4×4 后显存 | ≈2–3 MB | 5–7 MB（8 向 8–11 MB） | 约降至 1/6 |
| 首屏加载 | 3–6 MB | 7–19 MB（+2–4 s） | 需图集化，避免碎文件 |
| PNG 文件体积倍数 | 1× | 1.7–2.1× | 大图压缩率略优 |

### 4.3 加载与首包

- 移动端首屏必须在 3 s 内进入可交互，超出需拆分首包并显示进度。
- 图集化是硬要求：单文件 ≤2048×2048，避免数百个小文件带来的 IO 抖动。
- 纹理导入必须开启 ASTC/ETC2，否则低端机显存与包体双超。

### 4.4 制作成本

| 条目 | 720p | 1080p 手绘 | 1080p（3D 建模渲染成序列帧） |
|---|---|---|---|
| 玩家 4 向全套 | 4–6 人日 | 6–9（+50~70%） | 建模 3–5 + 绑定 2–3 + 动画 5–8 + 管线 2–3 ≈ 12–19 |
| 玩家 8 向全套 | 8–12 | 12–18 | 同上 +10~15% |
| 小怪（每种） | 2–3 | 3–5 | 6–10 |
| UI 图标 30 个 | 2–3 | 3–4 | — |

**结论**：手绘成本随分辨率线性增长；若需 8 向 + 装备换装，3D 建模渲染成 2D 序列帧的边际成本仅 10–15%，总成本更低（184 帧 1080p 渲染约 10–25 分钟/角色，属机器时间）。

### 4.5 稳定性影响

- 分辨率与缩放改动**不触及战斗逻辑、寻路、存档**，无数据迁移风险。
- 唯一已知回归点：`player_controller.get_lock_screen_rect()` 基于 `get_viewport_rect().size` 计算锁定候选范围，`lock_screen_margin=48` 以基准分辨率为单位；`zoom` 提升后实际物理边距变为 72 px。行为正确，但需在验收中确认锁定手感未变。
- `stage_a_check`、`stage_b_check` 不依赖窗口尺寸，改动后应保持全绿。
- 引入 `SubViewport` 后需确认 `FxLayer`（`z_index=100`，不进 `y_sort`）仍在世界层内，飘字不被 UI 遮挡。

## 5. 其他说明

### 5.1 结论

**建议推进，且以移动端为主线一次做对**，理由：

1. 项目零贴图零模型，现在是锁定规格的唯一零成本窗口。
2. 移动端真正的成本不在渲染，而在 **UI 分辨率无关化** 与 **资产规格决策**；这两项与是否上 1080p 无关，早晚都要还。
3. PC 1080p 在该架构下只是「`render_scale=1.0` + `zoom=1.5`」的一个档位，顺带完成，不需要第二套方案。
4. 「直接把 `1280×720` 改成 `1920×1080`」不成立：在移动端会同时破坏 UI 布局与视野一致性。

### 5.2 优先级与排期

| 优先级 | 动作 | 工作量 | 风险 |
|---|---|---|---|
| **P0** | 补齐移动端基线：横屏锁、`stretch/scale_mode`、纹理压缩开关；HUD 锚点化 + 血条比例化 + 字号 dp 化；设置面板居中 | 1–2 人日 | 低 |
| **P0** | 安全区契约落地：HUD 锚定内缩矩形，旋转/展开时重排 | 0.5–1 人日 | 低 |
| **P1** | 世界层 `SubViewport` + `render_scale` 三档 + `zoom` 归一公式；PC 1080p 作为高档验证 | 2–3 人日 | 中 |
| **P1** | 出《资产规格表》+ 试验资产包，真机验证采样与缩放 | 1–2 人日 | 低 |
| **P2** | `GameSettings` 增加「画质档 / UI 缩放 / 视野档」并持久化 | 1–2 人日 | 中 |
| **P2** | 触控契约收口：多指、幂等、暂停门控、热区补偿 | 1–2 人日 | 中 |
| **P3** | 美术量产（建议 3D 渲染成 2D 管线，输出 1080p 原生序列帧） | 数十人日 | 高 |

### 5.3 风险点

| 级别 | 风险 | 缓解 |
|---|---|---|
| **高** | 先做 720p 资产再上 1080p，等于全部重画 | P1 规格确认前不做批量美术 |
| **高** | 移动端首台目标设备不确定，导致二次适配 | 先定义「最低可接受设备」，以其为基线做全部预算 |
| **中高** | 非整数缩放 + nearest 采样导致像素抖动/摩尔纹 | 只提供离散档位；严格按 3.2 的 1:1 条件验收 |
| **中** | HUD 绝对坐标导致错位（40 处 offset + `HP_FILL_MAX` + 面板） | P0 完成，四类屏幕验收 |
| **中** | `Iso.TILE_W/H` 是逻辑与美术的耦合点，改像素尺寸波及其他 | 本方案不改常量 |
| **中** | 触摸模拟鼠标双路径重复触发 | 真机单指验收 + 幂等守卫 |
| **中** | 包体超限（8 向换装 14–19 MB 仅角色） | 分包 + ASTC + 复用图集 |
| **低** | 低端机填充率不足发热 | 0.7 渲染倍率 + 30 FPS 保底档 |
| **低** | 字体未入库、授权未核查 | 与 P0 一并收尾 |

### 5.4 验收标准（设备矩阵）

| 设备类 | 分辨率 / 宽高比 | 判定项 |
|---|---|---|
| 16:9 中端 | 1920×1080 | 默认档 60 FPS；可见格数 ≈400–500；文字无插值模糊 |
| 19.5:9 刘海 | 2340×1080 | 安全区内缩生效；血条不压刘海；按钮不贴手势条 |
| 20:9 宽屏 | 2400×1080 | 归一后可见格数与 16:9 偏差 ≤10%；HUD 贴边不越界 |
| 4:3 平板 | 2048×1536 | UI 可点、不裁切；允许 zoom 微调档 |
| 折叠屏 | 展开 2208×1768 | 展开/折叠切换时 HUD 重排一次且状态不丢 |
| PC 大屏档 | 1920×1080 / 2560×1440 | `zoom=1.5`，两档均无错位 |

**回归项**：`tests/stage_a_check`、`tests/stage_b_check` 全绿；`data/actors/*.json` 与 `Iso` 常量零改动。

### 5.5 术语表

| 术语 | 定义 |
|---|---|
| 逻辑渲染分辨率 | 世界层实际渲染的像素尺寸，与屏幕物理尺寸解耦 |
| 渲染倍率（render_scale） | 逻辑渲染分辨率 ÷ 屏幕分辨率，取值 0.7 / 0.85 / 1.0 |
| dp | 设备无关单位，`px = dp × dpi/160` |
| wu（世界单位） | 逻辑坐标单位，1 wu = 1 逻辑像素，图块 64×32 wu |
| 可见格数 | 屏幕内可见的等距格总量，= 可见世界面积 ÷ 1024 |
| 安全区 | 剔除刘海/挖孔/手势条后的可用矩形，HUD 的唯一布局基准 |
