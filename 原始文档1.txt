## 1. 项目概述

### 1.1 参考图片的可见特征

三张参考图呈现出典型的复古 2D 等距视角 MMORPG 视觉语言：

- **场景**：城镇、港口、森林、草地、石质建筑、遗迹和地下战斗区域。
- **镜头**：固定斜俯视角，场景以二维贴图构成，角色在地图上实时移动。
- **角色与怪物**：小比例角色精灵，头顶名称、等级或生命条；玩家、NPC、怪物共用一套场景实体管理机制。
- **战斗**：即时攻击、多怪同屏、近战/远程技能、火焰与冰霜等视觉效果、受击反馈和死亡效果。
- **成长**：等级、生命/魔法、装备槽、物品栏、技能快捷栏、经验与掉落。
- **城镇功能**：商人、任务 NPC、装备与物品商店、交易、角色状态面板。
- **导航**：小地图、坐标、地图切换与区域名称。
- **界面风格**：高信息密度、石木质感边框、传统 RPG 图标、文字标签和快捷按钮。

图片无法证明原游戏采用了什么引擎、服务器架构、寻路算法或资产格式。本方案只将可见特征作为设计参考，不依赖对原游戏内部实现的猜测。

### 1.2 项目目标

制作一个可玩的复古风格 RPG 原型，首先验证：

1. 等距地图显示、角色移动、碰撞和遮挡是否可靠。
2. 一套完整的敌人 AI：待机、巡逻、发现玩家、追击、攻击、受击、死亡、返回。
3. 一套完整的掉落系统：掉落表、随机数量、稀有度、拾取、背包入库。
4. 角色属性、装备、技能、怪物和物品均由数据驱动。
5. 形成可扩展的场景、UI、音效和美术资源规范。

**第一阶段不建议直接做大型 MMO 服务器。**先做离线可玩版本和完整战斗闭环；当玩法、性能和数据模型稳定后，再决定使用权威服务器实现联机。

## 2. 游戏范围与版本规划

### 2.1 垂直切片（第一可玩版本）

只制作一个小城镇、一张野外地图、一处洞穴或精英怪区域：

- 1 个可操作角色，至少 4 个方向移动；资源允许时做 8 方向。
- 1 套基础攻击和 2 个技能。
- 3 种普通怪物、1 种精英怪。
- 完整敌人 AI 和掉落系统。
- 20–30 种物品、6–10 件装备。
- 背包、装备栏、角色属性面板、简单商店。
- 1 个任务 NPC、1 条击杀任务。
- 角色死亡、复活或回城机制。
- 1 个存档槽位，支持保存与继续游戏。
- 基础 BGM、脚步/攻击/受击/死亡/拾取/UI 音效。

### 2.2 暂缓功能

在核心循环稳定之前，不优先制作：

- 大规模多人在线、跨服、行会和拍卖行。
- 数十张地图、复杂剧情分支和大量职业。
- 玩家交易、邮件、排行榜和经济系统。
- 复杂装备随机词缀、强化、镶嵌、合成全套系统。
- 大型副本编辑器、自动战斗、完整任务编辑器。
- 高成本全角色 8 方向全身装备换装。

这些系统会放大数据一致性、内容制作、测试和运维成本。应先验证单机核心玩法。

## 3. 核心玩法设计

### 3.1 玩家循环

1. 在城镇接受任务、整理背包、购买药水。
2. 进入野外地图。
3. 发现怪物，进入战斗。
4. 获得经验、金币或物品。
5. 拾取物品并检查背包容量。
6. 返回城镇出售垃圾物品、换装和补给。
7. 完成任务并解锁更危险区域。

每个环节都必须有可见反馈：提示文字、音效、动画、UI 数值变化或掉落物。

### 3.2 角色属性

建议第一版属性：

- `level`：等级。
- `exp`：当前经验。
- `hp / max_hp`：生命。
- `mp / max_mp`：魔法。
- `attack`：攻击力。
- `defense`：防御力。
- `attack_speed`：攻击间隔或攻速系数。
- `move_speed`：移动速度。
- `crit_rate / crit_damage`：暴击率和暴击倍率。
- `resist_fire / resist_ice`：元素抗性，可后续加入。

属性来源分层：基础成长 + 装备加成 + 临时效果。不要让 UI、装备和战斗各自重复计算属性；统一由 `StatCalculator` 或 `CharacterStats` 汇总。

### 3.3 战斗规则

建议采用易调试的第一版公式：

```text
effective_attack = attacker.attack + skill.flat_attack
raw_damage = effective_attack * skill.damage_multiplier
mitigated_damage = max(1, raw_damage - target.defense)
final_damage = apply_element_resistance_and_crit(mitigated_damage)
```

注意：

- 伤害计算应是纯逻辑函数，不直接依赖动画节点。
- 伤害判定由攻击逻辑触发，而不是仅凭动画播放到某帧就无条件造成伤害。
- 可用动画事件/AnimationPlayer 方法轨道在攻击有效帧触发 hitbox。
- 对范围技能使用形状查询或独立 `Area2D`，并对每个目标记录本次技能是否已命中。
- 处理无敌帧、击退、硬直、死亡中断、目标死亡后取消后续攻击等边界情况。

### 3.4 技能数据

技能应配置化，例如：

```json
{
  "id": "fire_bolt",
  "display_name": "火焰弹",
  "target_type": "single_enemy",
  "range": 180,
  "cooldown": 2.5,
  "mp_cost": 8,
  "damage_multiplier": 1.6,
  "projectile_speed": 320,
  "effect_scene": "res://effects/fire_bolt.tscn",
  "audio_event": "skill.fire_bolt"
}
```

技能配置中只放数据和资源路径；运行时技能控制器负责检查冷却、消耗、目标合法性、生成投射物和触发表现。

### 4.2 场景与模块边界

| 模块 | 职责 | 不应负责 |
|---|---|---|
| `GameManager` | 游戏状态、暂停、全局流程 | 直接实现怪物伤害公式 |
| `SceneRouter` | 地图/场景切换和加载流程 | 处理物品掉落规则 |
| `DataRegistry` | 读取并校验配置 | 保存运行时角色状态 |
| `PlayerController` | 输入、移动、目标选择、技能请求 | 决定服务器级权威规则（联网时） |
| `EnemyController` | 怪物状态机和行为决策 | 直接操纵背包 UI |
| `CombatService` | 攻击合法性、伤害、状态效果 | 播放所有 UI 动画 |
| `LootService` | 根据掉落表生成奖励 | 直接改 UI 节点 |
| `InventoryService` | 物品增删、堆叠、容量校验 | 决定怪物掉落概率 |
| `EquipmentService` | 装备穿脱和属性重算 | 负责角色精灵资源导入 |
| `QuestService` | 任务进度、条件与奖励 | 直接查询所有场景节点 |
| `AudioManager` | 音频总线、事件播放 | 在每个脚本里硬编码音量规则 |
| UI 控制器 | 展示状态、发出玩家操作请求 | 成为游戏数据的唯一来源 |

建议使用信号/事件解耦，例如 `health_changed`、`enemy_died`、`loot_spawned`、`inventory_changed`、`quest_progress_changed`。避免通过大量 `get_node("../../..")` 跨层访问。

### 4.3 等距坐标和排序

这是该类游戏最重要的底层问题之一。

如果地图采用二维菱形等距投影，可将逻辑网格坐标 `(u, v)` 映射到屏幕坐标：

```text
screen_x = origin_x + (u - v) * tile_width / 2
screen_y = origin_y + (u + v) * tile_height / 2
```

反向转换需根据地图原点和 tile 尺寸计算。Godot TileMapLayer 的本地坐标转换函数通常比手工公式更安全；应统一封装坐标转换，避免每个模块各写一套。

开发时必须区分：

- **逻辑坐标**：网格、寻路、格子占用。
- **世界坐标**：角色和物体在场景中的位置。
- **屏幕坐标**：鼠标点击、UI 指示和屏幕渲染位置。

不要把鼠标屏幕坐标直接当作地图逻辑坐标。

#### 遮挡排序

等距场景中的角色应能在树前、树后和建筑前后正确显示。推荐：

1. 地面图层单独渲染。
2. 可遮挡角色的对象使用独立场景或对象层。
3. 按对象脚底/基准点的世界 Y 坐标进行排序，而不是按贴图顶部。
4. 大型建筑拆分为地基、主体、前景遮挡层，避免一整张建筑图导致角色无法正确穿行。
5. 对多格物体和特殊建筑建立明确的排序规则，并制作专门测试地图。

### 4.4 角色移动与碰撞

- 输入方向先经过统一映射，再转换为等距世界移动方向。
- 对角线输入应归一化，避免斜向移动更快。
- 角色碰撞体尽量使用简单形状，碰撞基准点接近脚底。
- 视觉精灵和碰撞体分离：精灵可高于角色身体，碰撞体仍保持贴近地面。
- 建筑墙面、树干、岩石和不可通行区域需要碰撞。
- 点击移动可以作为后续功能；第一版优先完成键盘/虚拟摇杆移动和基本寻路。
- 寻路网格、碰撞层和视觉图层必须共享同一套阻挡定义或经过自动校验。

### 4.5 敌人 AI 状态机

建议使用明确状态，不要把所有 AI 写成一个不断膨胀的 `_process()`：

```text
IDLE（待机）
  └─ 到巡逻时间 → PATROL

PATROL（巡逻）
  ├─ 发现有效目标 → CHASE
  └─ 目标丢失/到达巡逻点 → PATROL 或 IDLE

CHASE（追击）
  ├─ 进入攻击范围且冷却结束 → ATTACK
  ├─ 目标超出追击范围 → RETURN
  └─ 目标失效 → RETURN

ATTACK（攻击）
  ├─ 攻击完成且目标仍有效 → CHASE / ATTACK
  ├─ 目标死亡 → RETURN
  └─ 自身死亡 → DEAD

HURT（受击）
  ├─ 受击硬直结束 → 回到先前有效状态
  └─ 生命值归零 → DEAD

RETURN（返回出生点）
  ├─ 到达出生点 → IDLE
  └─ 再次发现目标且允许重新仇恨 → CHASE

DEAD（死亡）
  └─ 播放死亡表现、结算掉落、延迟移除或回收
```

实现注意事项：

- 使用 `enum` 或独立状态类，确保进入/退出状态时重置计时器和动画。
- 目标引用必须检查是否仍有效、是否死亡、是否在同一地图和可攻击范围。
- 追击范围应有滞回：进入仇恨范围与脱战范围不同，避免边缘来回切换。
- 寻路不要每帧重算。按间隔更新目标路径，目标移动距离明显变化时才重新规划。
- 怪物返回出生点时要清理仇恨、异常状态和不应保留的战斗标记。
- 精英怪可扩展阶段机制，但不要让第一版普通怪物依赖复杂行为树。
- 同屏怪物数量增加后，采用分频更新、感知范围查询和对象池优化。

### 4.6 掉落系统设计

建议将掉落规则完全数据化，分为三层：

1. **怪物配置**：死亡经验、金币范围、引用哪个掉落表。
2. **掉落表**：多个掉落条目、概率、数量范围、稀有度和条件。
3. **掉落服务**：统一抽取、生成地面物品、拾取和入库。

示例掉落表：

```json
{
  "id": "forest_wolf_common",
  "entries": [
    {
      "item_id": "wolf_fang",
      "chance": 0.35,
      "min_count": 1,
      "max_count": 2
    },
    {
      "item_id": "small_health_potion",
      "chance": 0.08,
      "min_count": 1,
      "max_count": 1
    },
    {
      "item_id": "rare_ring",
      "chance": 0.005,
      "min_count": 1,
      "max_count": 1
    }
  ],
  "gold": {
    "min": 3,
    "max": 12
  }
}
```

上面的概率仅为示例，不能直接当作最终经济平衡值。每个条目的 `chance` 应明确表示“独立概率”还是“同一池权重”；两种规则不要混用。

#### 掉落处理流程

```text
怪物死亡
  → 标记死亡结算已执行
  → 结算经验和金币
  → 读取对应掉落表
  → 按配置抽取条目与数量
  → 在合法地面位置生成掉落物
  → 玩家进入拾取范围/点击拾取
  → 校验物品是否仍存在、背包是否有空间
  → 原子地加入背包
  → 移除地面掉落物
  → 更新 UI 并播放拾取音效
```

关键规则：

- 死亡结算必须幂等，避免动画回调和死亡信号重复触发造成双倍掉落。
- 背包满时不可静默删除物品，应提示玩家并保留地面掉落。
- 地面掉落需要生命周期、地图切换规则和拾取距离。
- 单机版可使用普通随机数；联网版不能信任客户端决定掉落结果，应由权威服务器结算。
- 掉落表需要统计测试：模拟大量击杀，核对实际掉率与理论概率。
- 应区分“独立掉落”“互斥掉落池”“保底掉落”等规则，并在配置格式中明确表达。
- 未来联网时，拾取操作需要唯一掉落 ID、归属权和并发校验，防止重复拾取。

### 4.7 背包、装备和物品

物品定义与物品实例应分离：

- **物品定义**：ID、名称、图标、类别、基础价格、是否可堆叠、装备属性。
- **物品实例**：数量、随机词缀、耐久度、绑定状态、唯一实例 ID（如需要）。

推荐基础物品类别：

- 消耗品：生命药水、魔法药水。
- 材料：兽牙、矿石、草药。
- 装备：武器、头盔、护甲、鞋子、戒指。
- 任务物品。
- 可出售的杂物。

背包服务需统一处理：加入、移除、堆叠、拆分、交换格子、装备/卸下、出售。所有操作先校验，再提交变更；UI 不应直接修改数据数组。

### 4.8 存档与数据版本

存档至少包含：

- 存档版本号。
- 玩家等级、经验、当前地图和安全位置。
- 属性中需要保存的永久状态。
- 背包和装备实例。
- 已接任务与任务进度。
- 已解锁地图或传送点。
- 关键世界状态（如需要）。

注意：

- 不要直接序列化整个节点树。
- 存档要有版本迁移函数，例如 `v1 -> v2`。
- 采用临时文件写入后替换正式文件的方式降低写入中断风险。
- 加载时校验物品 ID、地图 ID 和数值范围；配置中已删除的物品应有兼容处理。
- 需要区分“基础属性”和“由装备计算出的属性”，避免加载时重复叠加装备加成。

### 4.9 如果未来要做多人在线

联机化会显著增加复杂度，应在垂直切片完成后立项。推荐的原则：

- 服务器权威：角色位置、伤害、掉落、背包、交易和经济由服务器最终裁决。
- 客户端负责输入、预测和表现，不直接决定稀有物品掉落或金币数量。
- 明确玩家会话、地图实例、实体 ID、消息版本和断线重连。
- 对移动、攻击、拾取、交易等操作做频率限制与合法性校验。
- 设计服务端日志、监控、备份和数据迁移。
- 先做 2–8 人的小规模局域网/测试服务器原型，再验证同步策略与成本。
- 不建议把所有游戏状态塞进单一全局 RPC 或单一巨大管理脚本。

## 5. 策划与设计

### 5.1 世界与地图规划

第一版地图建议：

| 地图 | 用途 | 内容 |
|---|---|---|
| 新手城镇 | 安全区与教学 | 出生点、商人、任务 NPC、仓库/装备界面 |
| 森林外围 | 基础战斗 | 低级怪、基础材料、简单任务 |
| 森林深处 | 战斗进阶 | 更强怪物、精英怪、稀有掉落 |
| 小型遗迹/洞穴 | 小型挑战 | 狭窄通道、遮挡、特殊怪物与奖励 |

地图设计要明确：

- 出入口和安全区边界。
- 怪物刷出区域、数量上限和重生时间。
- 玩家出生点与复活点。
- 可通行区域和不可通行区域。
- 视线遮挡、交互点和场景触发区域。
- 地图音乐、环境声与战斗强度。
- 玩家离开后怪物是否重置、掉落物是否清理。

### 5.2 任务设计

第一版只需要任务模板：

- 与 NPC 对话。
- 击杀指定怪物。
- 收集指定物品。
- 返回 NPC 交付奖励。

任务状态可使用：

```text
LOCKED → AVAILABLE → ACTIVE → COMPLETED → CLAIMED
```

任务逻辑应监听游戏事件，例如 `enemy_killed`、`item_collected`，而不是每帧扫描整个世界。需要定义重复任务、失败条件、放弃任务和奖励领取是否可重复。

### 5.3 数值与经济

平衡工作应由表格或脚本驱动，不要把数值散落在代码中。

需要维护的表：

- 角色等级与经验曲线。
- 怪物生命、攻击、防御、经验和刷新时间。
- 装备等级、属性、售价和掉落来源。
- 技能消耗、冷却、范围和伤害倍率。
- 药水恢复量、价格和使用冷却。
- 怪物掉率与金币范围。

第一轮目标是“可玩且容易调试”，不追求复杂的经济模拟。使用自动模拟统计掉率、每分钟经验、金币收入、药水消耗和战斗耗时，再进行调整。

### 5.4 UI/UX 设计

参考图的界面信息量较大，但现代实现应提供可读性和可调整性：

- 主 HUD：角色头像、生命/魔法、等级、快捷栏、小地图。
- 角色面板：基础属性、装备槽、属性来源说明。
- 背包：网格、物品详情、分类、排序和容量提示。
- 商店：商品列表、价格、购买数量和确认。
- 目标信息：怪物名称、等级、血条。
- 战斗反馈：伤害数字、暴击提示、状态图标。
- 任务面板：目标进度、奖励、导航提示。
- 设置：音量、画面缩放、键位、UI 尺寸和文字大小。

必须处理鼠标悬停、点击、键盘焦点、拖拽物品、重复点击、窗口缩放和暂停时输入。移动端版本还需要触控目标尺寸、虚拟摇杆和技能按钮布局。

## 6. 美术资产规范

### 6.1 视觉风格

目标是复古、细节丰富、易读的 2D 等距幻想世界。建议建立风格基准图，统一：

- 等距投影角度和地面格子比例。
- 角色在屏幕中的高度和脚底基准点。
- 光照方向、阴影硬度和色彩饱和度。
- 角色轮廓、武器尺寸和技能特效亮度。
- 地图、角色、建筑、UI 的描边与材质风格。
- 角色、怪物、地面物品之间的对比度。

避免从多个素材包随意拼接，容易出现视角、透视、光源和像素密度不一致。

### 6.2 资产清单

#### 环境资产

- 地面：草地、泥地、石板、沙地、水面、洞穴地面。
- 边缘：悬崖、岸线、墙角、地面高低差。
- 建筑：房屋、商店、城墙、桥梁、遗迹、洞穴入口。
- 自然物：树木、灌木、石头、花草、枯木。
- 场景物：箱子、路灯、旗帜、篝火、船只、摊位。
- 环境动画：水面、火焰、烟雾、树叶、灯光闪烁。

#### 角色资产

- 玩家角色基础身体。
- 各方向移动、待机、攻击、受击、施法、死亡动画。
- NPC 外观与职业差异。
- 怪物基础模型/精灵、颜色或装备变体。
- 武器、盾牌、头盔、护甲、鞋子等可见装备。
- 角色阴影、脚底定位点和选择指示器。

#### UI 资产

- 背包格、装备槽、按钮、面板边框。
- 物品类别图标和稀有度边框。
- 生命/魔法/经验条。
- 小地图图标、NPC 标记、任务标记。
- 鼠标指针、目标框、状态效果图标。
- 字体与数字字形，确保中文显示完整。

#### 特效资产

- 普通攻击命中、暴击、格挡。
- 火焰、冰霜、闪电、治疗、护盾。
- 投射物轨迹、命中爆散、地面范围指示。
- 怪物死亡、掉落闪光、升级效果。
- 传送、复活和任务完成效果。

### 6.3 资产尺寸与导入规则

不要在项目开始时就锁死所有像素尺寸，应先确定目标角色和地砖尺寸，再按比例制作资产。

建议先做一套试验资产：

- 一块地面菱形 tile。
- 一个角色四方向待机/移动序列。
- 一只怪物的移动、攻击、受击和死亡序列。
- 一棵树、一栋建筑和一个前景遮挡对象。
- 一套 UI 面板和 10 个物品图标。

在 Godot 中验证缩放、滤镜、纹理边缘、动画帧对齐、排序和碰撞之后，再批量生产。

资产命名示例：

```text
env_grass_tile_01.png
env_tree_oak_a.png
char_player_idle_se.png
char_player_attack_ne.png
enemy_forest_wolf_walk_w.png
vfx_skill_fire_bolt_01.png
icon_item_wolf_fang.png
ui_panel_inventory.png
```

推荐规范：

- 文件名使用小写英文、下划线和稳定 ID。
- 原始文件与导出文件分开管理。
- 精灵序列明确帧尺寸、帧数、帧率和方向。
- 为每个动画记录原点、脚底点和碰撞体参考。
- 图标采用统一画布和留白规则。
- 使用版本控制追踪资源变化，避免直接覆盖导致回退困难。

### 6.4 动画制作要求

建议第一版角色至少包含：

| 动画 | 建议内容 | 触发条件 |
|---|---|---|
| Idle | 各方向待机 | 没有移动和动作 |
| Walk/Run | 各方向移动 | 有移动输入或移动目标 |
| Attack | 普攻动作 | 攻击进入有效状态 |
| Cast | 施法动作 | 技能开始 |
| Hurt | 受击 | 收到有效伤害 |
| Death | 死亡 | 生命值归零 |
| Use Item | 可选 | 使用药水或交互道具 |

攻击动画要标记有效帧；死亡动画播放完毕后再隐藏或回收节点。不要只根据动画结束事件判断伤害是否发生。

### 6.5 资产制作顺序

1. 风格探索图与比例测试。
2. 地面 tile 和基础地图。
3. 玩家角色与基础怪物。
4. 碰撞、遮挡和动画测试资产。
5. 战斗特效与掉落物。
6. 城镇建筑、NPC 和交互物。
7. UI 图标与面板。
8. 扩展地图与怪物变体。

先制作能够验证程序问题的最小资产集，再扩大内容量。占位图可以帮助开发，但应在项目早期建立替换规则，避免临时资产进入最终版本。

## 7. 音频设计

### 7.1 音频分类

| 音频类别 | 内容 | 触发方式 |
|---|---|---|
| BGM | 城镇、野外、洞穴、Boss 战 | 地图或战斗状态变化 |
| 环境音 | 风、鸟鸣、水流、洞穴回声、火焰 | 区域环境持续播放 |
| 角色音效 | 脚步、挥击、受击、死亡、施法 | 动画事件或战斗事件 |
| 怪物音效 | 待机、发现玩家、攻击、受击、死亡 | AI 状态和动画事件 |
| 技能音效 | 火焰、冰霜、闪电、治疗、护盾 | 技能表现事件 |
| UI 音效 | 打开面板、点击、装备、拾取、错误提示 | UI 操作 |
| 世界音效 | 门、宝箱、传送、任务完成 | 交互或任务事件 |

### 7.2 音频播放原则

- 建立独立的 `Master`、`Music`、`Ambience`、`SFX`、`UI` 音频总线。
- 2D 世界音效使用位置衰减；UI 音效不受世界距离影响。
- 高频率脚步、连续攻击和群体怪物声音需要限流或随机变体。
- 同一声音可以有多个音高/音量轻微变化的版本，减少机械重复感。
- BGM 切换时做短淡入淡出，避免突然截断。
- 特效音效与命中事件对齐，而非简单地在动画开始时播放所有声音。
- 提供总音量、音乐、音效和环境音设置，并持久化用户选择。
- 音频资源要记录来源、授权范围、署名要求、可否商用及修改权限。

### 7.3 最小音频清单

首个可玩版本建议至少准备：

- 2 首 BGM：城镇、野外。
- 1 首可选洞穴/精英战音乐。
- 4–6 个环境循环音。
- 6 个玩家动作音效。
- 每种首发怪物 3–5 个音效。
- 8–12 个技能/命中/死亡特效音效。
- 6–10 个 UI 音效。

先保证声音时机、混音和反馈正确，再增加音频数量。

## 8. 关键程序模块的验收标准

### 8.1 地图与移动

- 角色可在指定区域内移动，不穿过墙、树干和阻挡物。
- 对角线移动速度与直线移动速度一致。
- 角色可正确显示在树木/建筑前后。
- 鼠标点击地面与逻辑位置转换正确。
- 场景切换后角色位置、相机和地图边界状态正确。

### 8.2 敌人 AI

- 怪物能够待机、巡逻、发现、追击、攻击、受击、死亡和返回。
- 目标离开追击范围后，怪物不会无限追击。
- 路径受阻时不会每帧疯狂重算或卡死。
- 玩家死亡或切换地图时，怪物能够清理无效目标。
- 死亡结算只触发一次。

### 8.3 掉落与背包

- 每种怪物引用正确的掉落表。
- 数量范围、独立概率和互斥池规则经过测试。
- 地面物品可拾取，超出距离不可拾取。
- 背包满时有提示且物品不会丢失。
- 同一地面掉落物不能被重复领取。
- 装备穿脱后属性正确更新且不会重复加成。
- 存档读写后物品、数量、装备和任务状态一致。

### 8.4 战斗

- 攻击距离、冷却、消耗和目标合法性正确。
- 伤害、暴击、抗性和死亡规则可单元测试。
- 同一范围技能不会意外重复命中同一目标。
- 目标死亡时停止无意义攻击。
- 动画、伤害反馈、音效和飘字基本同步。

### 8.5 性能

第一阶段可先设定一个测试目标，而不是宣称所有设备都能达到：

- 在开发目标电脑上，普通野外场景 60 FPS 为目标。
- 测试 20、50、100 个敌人及不同数量特效的表现。
- 记录帧时间、寻路耗时、节点数量和内存占用。
- 对高频对象使用对象池前，先测量是否确实存在频繁创建/销毁瓶颈。
- 不要为了“优化”而过早把所有逻辑写成复杂 ECS；先保持结构清晰并进行实测。

## 9. 测试策略

### 9.1 测试类型

- **单元测试**：伤害计算、掉率抽样、属性合成、堆叠规则、经验升级。
- **集成测试**：杀怪 → 掉落 → 拾取 → 背包 → 装备 → 属性变化。
- **场景测试**：地形碰撞、遮挡排序、地图出入口、怪物刷点。
- **回归测试**：修复一个问题后重复跑核心流程。
- **性能测试**：怪物数量、技能特效、场景对象、长时间运行。
- **可用性测试**：背包操作、商店购买、任务领取、键位和 UI 缩放。

### 9.2 必测边界情况

- 怪物与玩家同时死亡。
- 玩家背包刚好只剩一个格子。
- 掉落物生成在不可通行地面。
- 目标在攻击动画中离开范围。
- 玩家在地图切换时被攻击。
- 存档写入过程中程序异常退出。
- 配置中引用不存在的物品或动画。
- 同一事件重复触发死亡结算。
- 暂停游戏时计时器、动画、音效是否符合预期。

## 10. 开发里程碑与任务拆分

以下工期是小型团队的初步估算，具体取决于人员经验、资产来源、每日投入和目标质量，不是保证交付时间。

### 阶段 A：技术验证

**目标：**确认等距地图、移动、碰撞、排序可行。

- 建立 Godot 项目与 Git 仓库。
- 制作一张小型测试地图。
- 实现玩家移动和摄像机跟随。
- 实现树木、建筑和角色的遮挡排序。
- 建立输入、暂停和场景切换。
- 输出技术验证记录和问题清单。

**验收：**角色能够在测试地图中正确移动，不穿墙，前后遮挡稳定。

### 阶段 B：敌人 AI 与战斗

**目标：**完成一套可复用的敌人战斗框架。

- 实现角色属性和基础攻击。
- 实现敌人状态机。
- 实现目标感知、追击、攻击和返回。
- 实现寻路、攻击范围和冷却。
- 实现受击、硬直和死亡。
- 实现伤害数字、基础技能和命中反馈。

**验收：**玩家可以持续战斗；怪物会追击和攻击，并在目标消失后返回。

### 阶段 C：掉落、背包与装备

**目标：**闭合“击杀—奖励—成长”循环。

- 建立物品定义和掉落表。
- 实现随机掉落、金币和经验。
- 实现地面掉落物、拾取距离和生命周期。
- 实现背包堆叠、容量限制和物品详情。
- 实现装备穿脱与属性重算。
- 实现存档和加载。

**验收：**击杀怪物可获得正确奖励，拾取和装备流程可靠，重启后存档数据一致。

### 阶段 D：地图、NPC 和任务

**目标：**建立完整的最小 RPG 循环。

- 制作城镇和野外地图。
- 添加商人、任务 NPC 和基础对话。
- 实现商店购买/出售。
- 实现击杀任务和收集任务。
- 实现地图切换、复活点和小地图基础功能。

**验收：**玩家能够接任务、出城、战斗、拿奖励、回城交任务和补给。

### 阶段 E：美术、音频和打磨

**目标：**将占位原型转化为具有统一风格的可玩版本。

- 替换主要角色、怪物、地形和建筑资产。
- 完成关键动画和技能特效。
- 加入 BGM、环境音和战斗/UI 音效。
- 调整 UI 排版、缩放、文字和输入反馈。
- 完成性能分析、兼容性测试和缺陷修复。

**验收：**完整流程可稳定游玩，视觉与音频风格一致，核心功能无阻断级缺陷。

## 11. 团队分工与交付物

| 2D 美术 | 地图、角色、怪物、建筑、图标 | 源文件、导出资源、动画表和命名清单 |
| 动画/VFX | 角色动作、技能特效、命中反馈 | 动画序列、事件帧、特效场景 |
| 音频 | BGM、环境音、技能与 UI 音效 | 音频文件、事件映射、授权记录 |
| QA/测试 | 功能、边界、回归和性能测试 | 测试用例、缺陷记录、验收报告 |

一个人开发时可以兼任多个角色，但仍应按这些职责分别管理任务和验收，不要把所有内容混在一个脚本或一张大表中。

---

## 12. 风险与常见坑

### 高风险

1. **遮挡排序最后才处理**：建筑和角色层级问题会影响地图资产切分，应该在技术验证阶段就解决。
2. **坐标体系不统一**：鼠标点击、寻路、碰撞和角色位置各用一套转换，后续会产生大量错位问题。
3. **AI 与动画耦合**：动画播放结束才改变状态，容易出现目标已死亡但怪物仍持续攻击等问题。
4. **死亡逻辑重复触发**：掉落、经验和金币可能重复结算。
5. **属性加成重复计算**：加载存档后再叠加装备属性，导致属性逐次增加。
6. **资产风格不统一**：不同素材包的视角、比例、光照和色彩不一致。
7. **过早做联网**：权威状态、同步、断线、反作弊和服务端部署会挤压核心玩法开发时间。

### 中风险

- TileMap、独立场景对象和前景遮挡层职责不清。
- 寻路每帧重算导致 CPU 消耗异常。
- 所有特效同时使用高分辨率透明贴图。
- UI 直接修改业务数据，造成背包与装备状态不一致。
- 配置缺少校验，错误 ID 到运行时才暴露。
- 存档没有版本号，更新后旧存档无法读取。
- 音效没有限流，群怪战斗时声音堆叠。
- 忽略中文字体、不同分辨率、窗口缩放和键盘焦点。

### 推荐的开发纪律

- 每完成一个模块就写最小可复现测试场景。
- 核心数值放入配置文件，不散落在脚本中。
- 为重要事件建立统一日志和调试开关。
- 所有掉落、奖励、交易操作都有明确的校验入口。
- 每个阶段必须有可演示版本和验收条件。
- 先解决正确性，再根据性能测量做优化。

## 13. 版权、素材和发布注意事项

如果参考现有游戏：

- 可以借鉴通用玩法和视觉语言，但不要直接复制原作的角色、地图、图标、音乐、名称、剧情、商标或受保护的资源。
- 只使用自己制作、明确授权或许可条件适用于项目的素材。
- 保存每个素材的来源、许可、作者署名和允许用途。
- 商用前核查字体、音效、贴图和第三方插件的许可。
- 如果后续发布联网版本，需要额外评估隐私、账号安全、用户数据、支付、服务器安全和地区法规。

## 14. 最终建议：第一周先做什么

按以下顺序推进，避免一开始就制作大量内容：

1. 建立 Godot 4.x 项目、Git 仓库和目录规范。
2. 创建一张只有地面、墙体、树木和建筑的等距测试地图。
3. 实现玩家移动、碰撞和相机跟随。
4. 验证角色脚底排序与建筑前后遮挡。
5. 创建一只怪物，完成待机、追击、攻击、受击、死亡和返回状态机。
6. 创建一个掉落表，让怪物死亡时生成物品。
7. 实现拾取、背包入库和背包满提示。
8. 加入一件装备，验证装备属性重算。
9. 添加存档/读档，验证重启后状态一致。
10. 再开始制作正式地图、角色、怪物、UI、特效和音频。

**第一阶段的完成标准不是“看起来像截图”，而是完成一个稳定的闭环：玩家进入地图 → 怪物发现并追击 → 玩家战斗并击杀怪物 → 怪物只结算一次掉落 → 玩家拾取并装备物品 → 属性正确变化 → 存档后可以继续游戏。**

这个闭环一旦稳定，扩展地图、怪物、装备、技能、任务和音频内容就会容易很多。
